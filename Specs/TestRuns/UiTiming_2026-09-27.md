# UI duration instrumentation — P0.1a

Date: 2026-09-27. Host: R1 (Windows x64), as recorded in
[MemoryPipeline_2026-09-27.md](MemoryPipeline_2026-09-27.md).

## Implemented scope

The production message pump, `Application::WindowProcedure`, completion drain, each final result apply,
deferred UI actions and host frame construction have optional duration scopes. Captures use a thread-local,
fixed histogram; tracing uses the existing `RedPrism.Pipeline` provider with keyword `0x4`. Disabled scopes
read no clock and allocate nothing. No new timer, polling loop, worker or wakeup is introduced.

These are inclusive elapsed durations, including nested dispatch or modal waits. Frame construction starts
after frame-latency readiness and includes the host layout/animation work and rendering through Present.
It is not GPU execution time or input-to-display latency. Dispatch and WndProc samples overlap. Clock samples
round up to microseconds; percentiles are bucket upper bounds and maxima are exact observed microseconds.

The checked-in WPR profile enables CPU samples, scheduler stacks, I/O and faults, graphics providers and all
three RedPrism keywords. Collector buffers total 24 MiB. The read-only `wpr -profiles` and `-profiledetails`
validation succeeds on this host; no system-wide recording session was started by this slice.

The new independent numeric/state checks cover all histogram bucket boundaries, exact maxima, nearest-rank
percentiles and total saturation; exact integer QPC conversion at and above 4 ms and at extreme frequencies;
nested capture restoration and worker isolation; actual posted-message dispatch; and actual scheduler result
and UI-action execution. Reentrant drains and empty action queues remain unmeasured no-ops.

The existing private in-process ETW test now decodes all six timing event names, exact sentinel durations,
message/job-class fields, keyword and owner thread. It verifies the 4 ms suppression boundary and worker
suppression, alongside the existing actual allocation/free proof and no-event-loss assertions. Ordinary
tests assert state and values only, never a timing target.

All 82 timing/histogram/trace checks pass per normal HostTests run; ASan repeats them in its stress invocation.
Every x64 build passes the linked ISA scan and compiled controls. All configurations pass both crash probes,
WARP self-test and nine harness captures. Native concurrency analysis was not rerun for this slice, which adds
no synchronization primitive; it remains a separate phase qualification from these runtime and cross-build gates.

## Measurement

`HostTests.exe --bench-ui-timing` ran three times in Release with the provider registered and no external timing
session. Each run has 31 batches of 20,000 empty scopes with capture off/on, including loop cost:

| Run | Disabled median / p95 / max, ns | Capture median / p95 / max, ns |
| --- | ---: | ---: |
| 1 | 4.4 / 4.8 / 4.9 | 43.1 / 45.6 / 49.2 |
| 2 | 4.4 / 4.7 / 5.1 | 43.2 / 46.1 / 46.9 |
| 3 | 4.4 / 4.7 / 4.8 | 42.4 / 42.8 / 42.9 |

Every disabled run recorded zero samples; each capture recorded exactly 620,000 with zero clock failures.
Logs are `C:\RedPrism.Perf\ui-timing-overhead-{1,2,3}.log`. These numbers include loop cost and measure empty
scopes only. They exclude enabled ETW serialization and do not qualify image speed or G1.

## Review and limits

Cheaper agents implemented histogram checks, the WPR profile and ETW test extensions. The primary reviewed and
integrated their work, implemented capture/hooks and scheduler tests, and replaced a floating conversion
fallback with exact overflow-safe integer division so a single tick remains observable at extreme frequencies.
An independent review confirmed the scope/clock ownership and led to an explicit 24 MiB WPR buffer-budget check.

P0.1 operation/IO baselines, real-loop scenario drivers and machine reports remain open. Image commands are
still synchronous pending P1. This slice establishes measurement instruments; it makes no claim about image
speed, RAW support, GPU acceleration or Photoshop performance. ARM64 cross-builds do not
substitute for runtime execution on a native ARM64 host.
